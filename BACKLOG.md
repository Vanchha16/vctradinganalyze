## 2. Architectural Decisions Deferred to Later Phases

- **RBAC permission tables.** `docs/23` §12–14 describes a granular permission model (roles *have* permissions, e.g. `signals.publish`), but `docs/03` only has a single `role` string column on `users` — no `roles`, `permissions`, or `role_permissions` tables exist anywhere in the schema. - **`docs/03` domain tables not yet built** (ai_analysis, signals, watchlists, watchlist_items, notifications, telegram_subscriptions, plans, subscriptions, invoices) are deferred to their respective roadmap phases (6–7), per the explicit phase-boundary decision made when scoping Phase 1.2B. ## 4. Security Enhancements Planned for Future Phases

- **Failed-login lockout** (docs/23 §17) — needs new `users` columns (`failed_login_attempts`, `locked_until` — not in `docs/03` currently) plus Redis-backed attempt tracking/backoff logic.
- **Temporary decision: login does not require `is_verified` (Phase 2B).** docs/23 §8 states email verification is "required before accessing protected access," but email-delivery infrastructure is explicitly deferred (see below), so no user could ever become verified. `AuthenticationService.login` therefore only checks credentials and `User.is_active`, not `User.is_verified` — otherwise every newly registered account would be permanently unusable. **This must be revisited once the email verification workflow exists**: either enforce `is_verified` in `login` at that point, or confirm the intent was always to gate it at the authorization/route level instead of at login.
- **Email verification flow** (docs/23 §8) — token generation/validation logic can be built, but real delivery is blocked on SMTP/Celery email infrastructure, which doesn't exist yet. Explicitly deferred during Phase 2A scoping.
- **Password reset flow** (docs/23 §9) — same email-infrastructure dependency as above. Must also invalidate old sessions on reset, per docs/23.
- **Future email delivery architecture** — both email verification and password reset depend on a not-yet-designed email subsystem (SMTP provider choice, templating, Celery task for async send, retry/failure handling). Needs its own design pass before either flow can be built, rather than being bolted on ad hoc to whichever flow is implemented first.
- **MFA** (TOTP, WebAuthn/passkeys, backup codes, trusted devices) — explicitly marked "(Future)" in docs/23 §10.
- **RBAC enforcement** — a permission-checking FastAPI dependency doesn't exist yet; blocked on the permission-table design noted above. Revisit `User.role` as a simple enum vs. a full `roles`/`permissions`/`role_permissions` schema if requirements grow.
- **Session/device management endpoints** (docs/23 §11 — list current/previous devices, logout current/other/all) — `UserSessionRepository.list_for_user` and `AuthenticationService.revoke_session`/`revoke_all_sessions` exist, but there's no API surface yet. **Deliberately excluded from Phase 2C** since `docs/04` doesn't spec a route contract for these — see §6.
- **`POST /auth/forgot-password`/`POST /auth/reset-password`** are listed in `docs/04` but **deliberately excluded from Phase 2C** (no underlying service logic exists yet; blocked on email infrastructure, per docs/04's Phase 2C update marking them "not yet implemented").
- **CAPTCHA after repeated failed logins** — explicitly "(Future)" in docs/23 §17.
- **Google OAuth login flow itself** (docs/23 §2) — only the `OAuthAccount` linking table + repository exist; the actual redirect/callback flow isn't built.
- **Token revocation strategy using `jti`** — access tokens carry a `jti` claim (unused) but no revocation mechanism has been designed. Refresh-token invalidation is handled (Phase 2B) by deleting the corresponding `UserSession` row (logout/revoke), but **access tokens themselves cannot be revoked before natural expiry** (15 min) — a compromised access token, or a role change, remains valid until it expires. Needs a decision on an access-token denylist (e.g. `jti` checked against Redis) if this window is judged too wide.
- **Audit logging wiring status (updated Phase 2B).** `AuthenticationService` now writes `AuditLog` entries for `login_success`, `login_failed`, `logout`, and `session_revoked`. Still not wired: password-reset, permission/role-change, and account-deletion events (docs/23 §18) — these can't be logged until those flows themselves exist.
- **`UserSession` has no `last_activity` column**, though docs/23 §6 lists it as tracked alongside device/browser/IP/created/expiration. Adding it needs a new migration, which was out of Phase 2B's approved scope (service-layer only, no schema changes). Revisit when device-management endpoints are built.
- **`AuthenticationService.revoke_session`/`revoke_all_sessions` exist as business logic (Phase 2B) but have no API surface yet** — docs/23 §11's device-management endpoints (list/logout current/other/all) still need routes built on top of these.
- **SQLite returns naive datetimes for `DateTime(timezone=True)` columns (institutional knowledge — do not rediscover).** Unlike Postgres, SQLite has no native timezone-aware datetime type, so a value written as UTC-aware comes back naive when read through the SQLite test/verification DB. `AuthenticationService._as_aware_utc` was added to normalize this before comparing `UserSession.expires_at` against `datetime.now(UTC)`. Any future code comparing timestamps read from the DB should account for this if it might run against the SQLite verification path.
- **Coverage tooling (`pytest-cov`) is not installed.** docs/06 §21 and docs/31 §10 set coverage goals (90%/95%), but nothing in `pyproject.toml` measures it yet. Test coverage for Phase 2A/2B has been verified by inspection (all success/failure branches have a test) rather than a numeric report.
- **CORS is broader than necessary.** `main.py` currently sets `allow_methods=["*"]` and `allow_headers=["*"]` with `allow_credentials=True` — flagged during the very first architecture review (before Phase 1.1 implementation). Should be scoped down to the actual methods/headers in use once the real API surface stabilizes.
- **Production JWT secret.** The dev placeholder in `.env.example` (`change_this_secret`, 18 bytes) triggers PyJWT's `InsecureKeyLengthWarning` in tests — expected for a placeholder, but a reminder that production deployments must set a real secret ≥32 bytes.
- **Additional security hardening ideas surfaced during Phase 2A** (not yet scoped to a phase): refresh-token rotation on use, per-session IP/user-agent binding for anomaly detection, and structured logging of auth failures separate from general app logs for easier SIEM ingestion later.
- **`email-validator` package is not installed.** Pydantic's `EmailStr` requires it, but it isn't in `pyproject.toml` and `uv` isn't available in this sandbox to add/relock it properly. Phase 2C's `RegisterRequest`/`LoginRequest` schemas use a plain `str` field with a basic regex pattern (`^[^@\s]+@[^@\s]+\.[^@\s]+$`) instead — sufficient for structural validation, but not RFC-compliant. Revisit adding `pydantic[email]` (or `email-validator`) as a real dependency in an environment where `uv add`/`uv lock` can run, then switch to `EmailStr`.
- **`fastapi.security.HTTPBearer` default behavior (institutional knowledge).** With `auto_error=True` (the default), a missing/malformed `Authorization` header raises `401 Unauthorized` (not `403`, which is a common assumption) in the FastAPI/Starlette version pinned here. Verified in Phase 2C via `test_me_rejects_missing_authorization_header`.
- **`httpx`'s `uv.lock` entry needs regenerating (Phase 3B).** `httpx` was promoted from the dev-only group to a declared runtime dependency in `pyproject.toml` (needed for `TwelveDataProvider`'s real HTTP calls), but `uv` isn't available in this sandbox to run `uv lock` and properly move/re-hash the entry - same limitation as the `email-validator` gap above. It was already installed transitively (via FastAPI's test client) so nothing breaks locally, but `uv.lock` should be regenerated in a real dev environment before this is considered fully clean.
- **Resolved in Phase 3C: `RequestValidationError` responses now match the standard error envelope.** FastAPI's built-in 422 handler for invalid query/body input returned its own `{"detail": [...]}` shape, never overridden since Phase 1 - inconsistent with the `{"error", "message"}` convention every other failure uses. Existed since Phase 2C but only became visible once a phase had meaningfully-validated query parameters (`timeframe`, indicator names) that users would routinely get wrong. Fixed in `app/exceptions/handlers.py`.
- **A genuinely flaky pre-existing test was found and fixed in Phase 3C: `test_decode_token_rejects_tampered_signature`.** It tampered only the *last* character of a JWT signature, which - depending on the signature's exact byte length - can encode only padding/insignificant bits, occasionally letting the "tampered" token verify successfully anyway (reproduced failing 1-in-3 isolated runs). Fixed to tamper the *first* character of the signature segment instead, which is always significant (verified stable across 20+ isolated runs after the fix). Worth remembering if any other test ever tampers JWT bytes by touching only the last character.

## 5. Database Refinements and Migration Notes

- **Alembic `server_default` dialect gotcha (institutional knowledge — do not rediscover).** Column *types* in autogenerated migrations render dialect-neutrally (`sa.Uuid()`, `sa.JSON()`, etc.), but `server_default` SQL expressions are compiled against whatever dialect is *connected* at generation time. Generating against our temporary SQLite verification DB has twice produced `server_default=sa.text('(CURRENT_TIMESTAMP)')`, which is invalid Postgres syntax — both times caught and manually corrected to `sa.func.now()` before committing. **Every future migration must be checked for this before committing.** Worth writing up as a short note in `docs/06` or a dedicated migrations runbook so it's not tribal knowledge only visible in chat history.
- **SQLite requires the `foreign_keys` pragma to be enabled explicitly for tests.** Unlike Postgres, SQLite does not enforce foreign-key constraints by default — repository/model tests that verify FK behavior (e.g. cascade or restrict on delete) must set `PRAGMA foreign_keys=ON` on the test connection/engine, or the tests will silently pass even if the constraint would fail against real Postgres. Verified during Phase 2A when testing `User`/`OAuthAccount`/`UserSession`/`AuditLog` FK relationships.
- **No migration has ever been verified against real Postgres.** This sandboxed dev environment has no reachable Postgres server; all migrations (`system_settings`, auth tables) have only been round-trip verified against temporary SQLite databases (upgrade → downgrade → upgrade → `alembic check`). Recommend running the full migration chain against actual Postgres (e.g. `docker compose up -d db` then `alembic upgrade head`) at least once before any real deployment.
- **`system_settings.value`** is a plain `Text` column since `docs/03` doesn't specify a type. If settings need typed values later (booleans, numbers, structured JSON), may need a `value_type` discriminator column or a switch to a JSON column.
- **Data retention** (`docs/03` §18 — e.g. notifications deleted after 90 days, price candles archived after 2 years) has no implementation yet; not relevant until the corresponding tables exist, but will need scheduled cleanup jobs (likely Celery beat) eventually.
- **Resolved in Phase 3.5: CI now tests the migration path against real PostgreSQL.** `.github/workflows/ci.yml` runs a `postgres:17` service container and executes `alembic upgrade head`/`alembic check` against it before the test suite — this will now catch a `server_default` (or any other dialect) issue automatically on every push/PR, rather than relying on manual verification each time. This is still separate from actually validating this specific sandbox's local Postgres — see the new note below.
- **A real, already-running local PostgreSQL was discovered on this machine (port 5432) while adding CI's Postgres verification (Phase 3.5), but was deliberately not used.** `netstat`/`tasklist` showed a `postgres.exe` Windows service already listening on `5432` — unknown credentials, unknown purpose, and not part of this project's own Docker setup. Connecting to it or creating a database on it wasn't attempted without the user's explicit go-ahead, since it's a shared system resource outside the project's control. If the user wants to use it to manually validate migrations locally (rather than only via CI's ephemeral container), that's a deliberate follow-up action, not something to do unilaterally.

## 9. Development Environment Differences (SQLite vs. PostgreSQL)

**This is the canonical place to record behavioral differences between SQLite (used for local development, unit tests, and migration verification) and PostgreSQL (the production database, per ADR-003 and docs/06 §2). Add new entries here as they're discovered — don't let them live only in chat history or a single test's docstring.**

- **Timezone-aware datetime behavior.** SQLite has no native timezone-aware datetime type, so a `DateTime(timezone=True)` value written as UTC-aware comes back **naive** when read through SQLite, even though Postgres preserves the offset correctly. Discovered in Phase 2B when comparing `UserSession.expires_at` (read from the DB) against `datetime.now(UTC)` raised `TypeError: can't compare offset-naive and offset-aware datetimes`. Fixed with a normalizing helper (`AuthenticationService._as_aware_utc`) rather than assuming the value is already aware. **Any code that compares a datetime read from the DB against a fresh `datetime.now(UTC)` must account for this if it may run against the SQLite path.**
- **Alembic autogenerate `server_default` differences.** Column *types* render dialect-neutrally in autogenerated migrations, but `server_default` SQL expressions are compiled against whichever dialect is *connected* at generation time. Generating against the SQLite verification DB has twice produced `server_default=sa.text('(CURRENT_TIMESTAMP)')`, which is invalid Postgres syntax — both times caught and manually corrected to `sa.func.now()` before committing (see §5 for full detail). **Every future migration must be checked for this before committing.**
- **`foreign_keys` pragma requirement.** Unlike Postgres, SQLite does not enforce foreign-key constraints by default. Repository/model tests that verify FK behavior (cascade or restrict on delete) must explicitly enable `PRAGMA foreign_keys=ON` on the test connection/engine, or the tests will silently pass even if the same constraint would fail against real Postgres (see §5, discovered in Phase 2A).
- **No migration has been run against real Postgres from within this sandbox's own tooling, though CI now does (Phase 3.5).** `.github/workflows/ci.yml` runs a real `postgres:17` service container and executes `alembic upgrade head`/`alembic check` against it on every push/PR (see §5). Locally, migrations are still only round-trip verified against temporary SQLite databases — a real, unrelated `postgres.exe` service was found already running on this machine (port 5432) during Phase 3.5, but wasn't used pending the user's explicit go-ahead (see §5).
- *(Add future SQLite/Postgres behavioral differences here as they're found — e.g. JSON column semantics, case-sensitivity of text comparisons/`LIKE`, or numeric precision, none of which have been hit yet but are plausible candidates.)*
- **Resolved (2026-08-06): the test-isolation-from-ambient-`.env` defect described below is fixed.** `backend/tests/conftest.py` now sets `os.environ[...]` for every provider list (`MARKET_DATA_PROVIDERS`, `NEWS_PROVIDERS`, `ECONOMIC_CALENDAR_PROVIDERS`, `TELEGRAM_PROVIDERS`) back to their documented `["mock"]` default and blanks every real API key (`TWELVE_DATA_API_KEY`/`NEWS_API_KEY`/`ECONOMIC_API_KEY`/`OPENAI_API_KEY`/`TELEGRAM_BOT_TOKEN`), at module top level, before any `app.*` import - pydantic-settings' precedence (init args > OS env > `.env` file > field defaults) means this overrides `.env` without editing or reading it. `ai_orchestrator_providers` is deliberately left at its own default (`["openai"]` - it has no `"mock"` implementation to fall back to); blanking `OPENAI_API_KEY` is what neutralizes it, since `OpenAIProvider.generate()` raises immediately on an empty key rather than making a real call. Also added (recommended-not-required, per the build spec) an autouse `socket.socket.connect` guard that raises on any non-loopback connection, to catch this whole class of problem recurring; verified it doesn't break any of the 931 tests before keeping it. Both previously-failing tests now pass; full suite is 931 passed, 0 failed.
- **A genuine (if minor) test-isolation defect, not a SQLite/Postgres difference: `tests/test_market_data_dependencies.py::test_get_market_data_providers_returns_rate_limited_mock` fails on this machine because it reads real local config.** `backend/.env` sets `MARKET_DATA_PROVIDERS=["twelve_data"]` (real production config, set for Phase 7E's live-data activation) while the test asserts the *default* resolves to the `mock` provider - so locally the test observes `twelve_data` and fails. It passes in CI, which has no `backend/.env` and so falls through to the real default. This means the local suite can never be fully green on this machine, which is worse than it sounds: a genuine regression in this dependency could hide in the noise of an already-failing local run. The fix is to isolate the test from ambient `.env` config (e.g. explicitly overriding/clearing `MARKET_DATA_PROVIDERS` in the test's settings fixture) rather than relying on whatever happens to be in the environment - not done here, this is a record of the defect only. Recorded here rather than under a "SQLite vs. Postgres" heading because the cause is unrelated to either database; this section was the closest fit among the environment-difference/test-tooling sections in this file.

A 1GB swap file was added as headroom; steady-state shows ~330MB swap in use with the full stack (backend + worker + beat + frontend + Postgres + Redis) running simultaneously - stable, not thrashing, but worth monitoring, and a candidate for a larger instance if load increases. Disk is similarly tight (6.8GB total, ~1.2GB free after this deployment) - `node_modules`/`.next` build artifacts and apt/npm caches are the main consumers; watch this before any future `npm install`/rebuild on the same box. `ALLOW_PUBLIC_REGISTRATION` correctly defaults closed in production (verified live: `POST /auth/register` returns `403`). The first Super Admin still needs to be bootstrapped via `backend/scripts/create_admin.py`, run directly by the operator over SSH (not automated, per ADR-123) - not yet done as of this deployment.

## 13. Smart Money Concepts Engine (Phase 4B) — Deferred Items and Discoveries

- **`smc_events` rows for zone-type concepts (Order Blocks, FVGs, Liquidity Zones) are mutable**, a first for this project - every other table (`price_candles`, `indicator_results`, `audit_logs`) is append-only. See ADR-033/ADR-037. Do not copy this pattern to a new table without the same "genuinely evolving single entity, not a sequence of discrete facts" justification.
- **Incremental scanning is bounded-window, not true delta-only** (docs/43 §15). Each `analyze()` call re-examines the most recent 500 candles regardless of how much genuinely new data arrived since the last call; persisted events are de-duplicated by natural key so repeated calls don't accumulate duplicates, but the *work* isn't skipped, only the *storage*. A true delta-only scan (fetching only candles newer than `SMCProcessingState.last_processed_timestamp`, and only re-checking currently-unresolved zones against them) is a real future optimization if history sizes or request volume grow enough to matter.
- **`SMCProcessingState.engine_version` is recorded but not yet acted on.** No migration/recovery logic reads it back to decide whether stored events need re-validation after an algorithm change - it's bookkeeping for a future phase to use, not yet load-bearing.
- **Four concepts referenced during Phase 4B planning were deliberately excluded** because docs/09_SMC_ENGINE.md never documented them: Inverse Fair Value Gaps (IFVG), an Internal/External BOS distinction, a dedicated Displacement analyzer, and Market Imbalance. If a future phase wants these, they need their own documentation and ADR first, per "never invent architecture" - don't add them quietly.
- **API filtering query params were considered but not implemented** - `GET /analysis/smc/{symbol}` returns all currently-non-archived events for the timeframe; `event_type` and `include_mitigated` filters were discussed during planning as a natural addition given persistence, but deferred to keep Phase 4B's scope to what was explicitly approved.
- **Order Block strength/freshness scoring and volume confirmation use simple, deterministic heuristics**, not Technical Analysis's ATR/relative-volume indicators (deliberately decoupled, docs/43 §10) - revisit if these prove too coarse in practice.
- **The 30-day archive threshold (ADR-037) and the 5-basis-point equal-highs/lows tolerance (ADR-035) are considered starting points**, not tuned models - flagged in their respective ADRs for revisiting once real outcomes can inform tuning.
- **Coverage tooling still not installed** (see §4) - Phase 4B's 59 new tests were likewise verified by inspection (every analyzer, lifecycle transition, and API path has a dedicated test) rather than a numeric coverage report.
- **Replay/backtest mode for historical SMC validation - not yet designed.** Requested on approval of Phase 4B as a future consideration: a mode that re-runs `SMCEngine` against a historical candle range as if scanning it candle-by-candle in real time (rather than the current single bounded-window pass over the most recent data), to validate detection quality/lifecycle transitions against known historical outcomes. Would likely need its own entry point (not the live `analyze()` path, since that always anchors to "now" and the most recent `_DEFAULT_LOOKBACK` candles) and a decision on whether it writes to `smc_events` at all or produces an isolated, non-persisted result. No design work done yet - flagged for a future phase.

## 14. Market Regime Engine (Phase 4C) — Deferred Items and Discoveries

- **`MarketRegimeEngine` is stateless (ADR-038), like Technical Analysis (ADR-027) and unlike SMC (ADR-032/ADR-033).** No `market_regime` table exists; every call re-derives its classification from a fresh `TechnicalAnalysisEngine`/`SMCEngine` pass rather than reading persisted history. If a future phase needs historical regime snapshots, that requires a new ADR and migration, not a quiet addition.
- **Classification precedence (ADR-039) is a same-request tie-break rule, not a confidence override.** `RegimeClassifier` evaluates every candidate regime's confidence first, and only applies precedence ordering among qualifying candidates - a low-confidence regime can never win over a high-confidence one just because it's earlier in precedence. Worth remembering given how easy it would be to mis-implement this as "first qualifying regime wins."
- **Classification Stability (ADR-044) is explicitly *not* true cross-request hysteresis.** It's a same-request anti-oscillation margin check only (Market Regime has no persisted state to compare against across requests, per ADR-038). True hysteresis was considered and deliberately deferred - see docs/44 and the CHANGELOG's Phase 4C entry. Revisit only if/when Market Regime gains persistence.
- **`compatible_strategies`/recommendation fields were deliberately excluded from engine output (ADR-043).** docs/16 §16/§17's strategy-compatibility and AI-integration guidance remain documentation-only - the engine returns classification/confidence/evidence, never a BUY/SELL/WAIT recommendation or strategy suggestion. Don't add these to the engine without a new ADR; that's the AI Orchestrator's job (Phase 6).
- **Pullback Depth (Market Regime) is deliberately distinct from SMC's Pullback concept (ADR-041).** Market Regime's version is a single-timeframe retracement-depth measurement; SMC's is multi-timeframe. Don't conflate or merge these - they answer different questions and were kept separate on purpose.
- **Accumulation/Distribution's definition (ADR-040) is deterministic and reuses SMC's Order Block/liquidity-sweep directionality**, not a fresh volume-profile calculation - consistent with docs/44 §5's reuse-first design (Market Regime is "almost entirely" derived from Technical Analysis's and SMC's already-computed evidence).
- **`TechnicalAnalysisResult` gained new fields (`trend_evidence`/`momentum`/`oscillator`/`volatility`/`volume`) purely so Market Regime could consume analyzer-level evidence that Technical Analysis was already computing and discarding before reaching its public dataclass.** This was an additive-only change (no existing field removed/renamed) - safe for any existing consumer of `TechnicalAnalysisResult`, but worth knowing this evidence now flows through Technical Analysis's public contract, not just internally.
- **No API filtering/query params beyond `timeframe` were added** - `GET /analysis/market-regime/{symbol}` and its `/multi-timeframe` variant return the full classification; no equivalent of SMC's discussed-but-deferred `event_type`/`include_mitigated` filters was considered, since there's no persisted event list to filter here.
- **Coverage tooling still not installed** (see §4) - Phase 4C's 59 new tests were likewise verified by inspection (every analyzer, the precedence-vs-raw-confidence regression case, and both new API paths have dedicated tests) rather than a numeric coverage report.
- **Confidence Engine (Phase 4D) is now complete** - see §15 below. `app/services/market_regime/confidence_engine.py` (`RegimeConfidenceEngine`, ADR-042/docs/44) remains regime-classification confidence only, distinct from the standalone `AnalysisConfidenceEngine` built in Phase 4D (ADR-048).

- **Spread and Risk/Reward requirements (Scalping's "Low Spread," Swing Trading's "Healthy RR") are excluded from their strategies' Evidence Quality denominators** (ADR-074) - same "no spread data source, no candidate setup" gaps already tracked for Risk Management (§18, ADR-065). - **The Risk component's sub-penalties (session-closed/low-liquidity/critical-event/extreme-volatility) and the 50-point rejection floor are hand-tuned starting points, not empirically calibrated** - same caveat as every prior scoring table (ADR-028/030/035/036/037/042/046/055/059/060/064). Revisit once real usage data exists.
- **Swing Trading's "Higher Timeframe Trend" (docs/17 §13) uses the requested timeframe's own trend-strength evidence, not a genuine separate higher-timeframe fetch** - a deliberate scope simplification (docs/49 §11), not an oversight. - **A `WatchlistItem`-only count query can't reuse `BaseRepository._count` (institutional knowledge - do not rediscover).** `BaseRepository[ModelType]._count` is generically typed against `self.model` (a repository's primary table) - `WatchlistRepository.model = Watchlist`, so a `Select[tuple[WatchlistItem]]` passed to `self._count()` fails mypy strict (`incompatible type "Select[tuple[WatchlistItem]]"; expected "Select[tuple[Watchlist]]"`). - **Timezone display bug discovered during 7D-B's manual walkthrough (pre-existing, not introduced by this phase, out of scope to fix here).** A watchlist's `created_at` displayed as "7 hours ago" immediately after creation instead of "a few seconds ago." Root cause: SQLite returns naive datetimes (§9's documented gotcha) - `Watchlist.created_at` comes back tzinfo-less from the local dev DB, Pydantic serializes a naive `datetime` to JSON *without* a `Z`/offset suffix (e.g. `"2026-08-06T02:49:43"`), and the browser's `new Date(value)` (used by `lib/format.ts`'s `formatRelativeTime`/`formatDateTime`) then parses a timezone-less ISO string as **local time**, not UTC - on a machine set to UTC+7 this reads a UTC instant 7 hours earlier than it actually is. This is systemic, not Watchlists-specific: every timestamp field returned by any endpoint (signals, ai_analysis, news, etc.) is affected identically whenever running against the local SQLite dev DB; it would not reproduce against Postgres, which preserves the UTC offset. Not fixed here - out of scope for a frontend-only Watchlists phase, and the real fix (backend: always serialize UTC-aware; or frontend: append `Z` before parsing if no offset is present) needs its own decision, not a quiet patch inside an unrelated feature phase.
